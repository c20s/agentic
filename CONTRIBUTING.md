# Contributing

This repo is an `apm` package: a source of Claude Code / GitHub Copilot skills and agents that others install with `apm install c20s/agentic`. Read this before adding or changing a primitive.

## Setup

```sh
curl -sSL https://aka.ms/apm-unix | sh   # install the apm CLI (macOS/Linux)
```

## Where things go

All source lives under `.apm/`. Nothing else is deployed.

| Primitive | Path | File |
|---|---|---|
| Skill | `.apm/skills/<skill-name>/` | `SKILL.md` |
| Agent | `.apm/agents/` | `<agent-name>.agent.md` |
| Instructions | `.apm/instructions/` | `<name>.instructions.md` |
| Prompt | `.apm/prompts/` | `<name>.prompt.md` |

Never hand-edit `.github/` or `.claude/` — those are generated by `apm compile` and overwritten on every install.

## Adding a skill

Read Anthropic's [skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) first. This repo adds a few of its own rules on top:

1. Create `.apm/skills/<skill-name>/SKILL.md`. The folder name and the frontmatter `name` must match: lowercase letters, numbers, and hyphens only, 1–64 characters, no leading, trailing, or doubled hyphens. Use a verb-ing name (`processing-pdfs`) or a short noun phrase. Don't use vague names like `helper` or `utils`.
2. Write `description` in third person. Say what the skill does and when to use it ("Use when…", "Apply when…"). Don't write "I can help…" or "You can use this…" — that breaks discovery.
3. Write the body as headlines and short bullet points, not paragraphs.
4. Keep a point inline if it's short and always useful — a one-line rule, a naming constraint, a short code example. Most points should stay this way. Only move a point into `references/<case-name>.md` if it's long, or only needed sometimes. Ask: would most tasks skip this file? If yes, it's a good reference. If every task needs it, keep it in `SKILL.md`.
5. When a bullet links to a reference, write it as a plain Markdown link: `[short label](references/<case-name>.md)`. One bullet links to one file. If two bullets want the same file, merge the bullets.
6. A reference file should not link to another reference file. If you need that, the skill is probably two skills. Add a short contents list at the top of any reference file over 100 lines.
7. Keep `SKILL.md` under 500 lines. If it's getting long, move more into references instead of writing more.
8. Before writing much, try the task without the skill. Write down exactly what went wrong. Write only the instructions that fix those problems — don't guess at problems you haven't seen.
9. Before committing, run:

   ```sh
   apm compile --validate
   apm compile -t claude
   apm compile -t copilot
   ```

### Skill directory shape

```
.apm/skills/<skill-name>/
├── SKILL.md                     # headlines + bullets; short points stay inline, long ones link out
└── references/
    ├── <case-one>.md            # only long or situational detail
    └── <case-two>.md
```

`SKILL.md` body shape:

```markdown
## Reviewing plans

- Put `terraform plan` output in a fenced code block, never pasted raw.
- Flag any module pin that isn't exact. See [module pinning](references/module-pinning.md) for the full decision tree.

## Writing modules

- Variables need a `description` and a `type`.
```

The first and third bullets are short, always-true rules, so they stay inline. The module-pinning bullet links out because the full guidance is long and only needed when that case comes up.

### Adding scripts to a skill

A skill can ship real code, not just Markdown. If a task is better done by running a script than by asking Claude to write one on the spot, add a `scripts/` folder next to `SKILL.md`.

```
.apm/skills/<skill-name>/
├── SKILL.md
├── references/
└── scripts/
    └── <name>.ts            # or .js — run with bun
```

- Tell Claude to run the script, not to read and re-type it. In `SKILL.md`: "Run `scripts/convert.ts` to do X," with the exact command.
- The first time a skill runs a script, it must check the runtime is available first, for example `bun --version`. If it's missing, say so clearly instead of guessing or silently falling back to something else.
- A script should handle its own errors and print a clear message. Don't write a script that just crashes and leaves Claude to guess why.
- Don't put example code in `SKILL.md` that's meant to be run — put it in `scripts/` and call it from a bullet instead. A bullet like `- Run scripts/validate.ts to check output.` is enough.

## Adding an agent

1. Create `.apm/agents/<agent-name>.agent.md`.
2. Required: `description`. Recommended: `name` (don't use `default` or `start` — they collide with `apm run` script resolution).
3. Optional: `model`, `tools` (whitelist — format differs per target, check how the target harness expects it), `color`, `handoffs`.
4. The Markdown body after frontmatter is the system prompt.
5. Note: Windsurf and Gemini don't support `.agent.md`. If an agent needs to reach those targets, author it as a skill instead.

## Adding instructions

1. Create `.apm/instructions/<name>.instructions.md`.
2. `description` is required. Add `applyTo` (a glob, comma-separated globs, or a YAML list of globs) to scope the rule to matching files; omit it only for a genuinely global rule, since unscoped rules get folded into compiled context files like `AGENTS.md` for every target.

## Versioning

Bump `version` in `apm.yml` (SemVer, quoted) whenever primitives change in a way consumers should pick up. Tag releases (`vX.Y.Z`) so consumers can pin:

```sh
apm install c20s/agentic#v1.2.0
```

## Before opening a PR

```sh
apm compile --validate   # frontmatter + structure
apm audit                # hidden-unicode / supply-chain scan, drift check
apm compile -t claude && apm compile -t copilot   # confirm both targets build
```

Install the branch into a scratch repo and sanity-check the deployed output before merging:

```sh
apm install c20s/agentic#<branch-name>
```

Commit `apm.lock.yaml` if it changed. Don't commit changes under `.github/` or `.claude/` by hand — regenerate them with `apm compile`.

## Style

- One skill = one trigger condition. If a skill covers two unrelated situations, split it.
- No comments explaining *what* code/instructions do — write the instruction clearly instead.
- Prefer editing an existing skill/agent over adding a near-duplicate.
